1. Problem Statement¶

I'm framing this around a streaming platform's A&R and playlist team. Thousands of new tracks land in the catalog every day, and only a fraction get pushed into editorial playlists or marketing pushes. Right now that decision is largely manual and reactive: someone waits for early stream counts before a track has had a real chance to prove itself. If the team had a decent popularity estimate straight from a track's audio characteristics (already computed by Spotify's own analysis pipeline for every track), they could prioritise promotion earlier and more consistently instead of waiting to see what sticks. Catching a track's potential even a week sooner can change its trajectory; missing it just means a competitor platform gets there first.

I've set this up as a regression problem: predict a track's popularity score (0–100) from its audio features (danceability, energy, tempo, loudness, etc.), its genre, and whether it's marked explicit. Regression made more sense to me than a binary hit/flop classifier, mainly because popularity isn't really a yes/no thing — a numeric score is far more useful for ranking catalog entries than a hard cutoff would be.

Features and popularity scores come from the Spotify Tracks Dataset (Pandya, 2023) on Hugging Face: 114,000 track entries across 125 genres, each carrying Spotify's own audio-analysis features plus a popularity score. I removed exact duplicates and tracks that were repeated across multiple genre listings (the source lists a track once per genre it's tagged with), which left about 89,740 unique tracks — see pipeline/curate_spotify.py for that step. Free-text identifier columns (artist, album, track name) were dropped too, since they don't generalise as model inputs.

Two things stood out here. About 10.5% of tracks sit at exactly zero popularity — plausibly tracks that just haven't accumulated enough plays yet, rather than genuinely "worthless" tracks. I'm treating that as a floor effect worth flagging rather than fixing: those rows aren't being removed, since they're still valid low-popularity examples, but it's worth noting the score is right-censored at the bottom. Second, and more important for modelling, every raw audio feature correlates only weakly with popularity (|r| under 0.13 across the board). That alone rules out a simple linear model doing well here, and it's part of why genre gets engineered in as a feature in the next section — popularity probably has a lot more to do with what kind of music it is than with how it measures acoustically.

Evaluation metrics. Since this is regression on a bounded 0–100 score, I'm using MAE as the primary metric — it's directly interpretable as "predictions are off by X popularity points on average" — with R² as a secondary check on how much of the variance in popularity the model actually explains beyond a mean-only baseline.

3. Data Preprocessing & Feature Engineering¶

Steps: cap duration_ms at the 99th percentile to tame the long tail identified above; one-hot encode track_genre (113 columns) since genre is categorical and, per the correlation check, likely carries real signal that individual audio features don't; cast explicit to int; split 70/15/15 into train/validation/test; and fit a StandardScaler on the training set only (then apply it to val/test) so no information leaks across the split. The target is rescaled to 0–1 for training stability and converted back to the 0–100 scale whenever I report a metric.

4. Model Training¶

I'm using a plain feed-forward network (multilayer perceptron) in Keras rather than a CNN/RNN — there's no spatial or sequential structure in this tabular feature set, so dense layers are the right tool. The harness below builds and trains one configuration; I reuse it for every run in the experiments section rather than repeating near-identical code per model.

In [4]:
import tensorflow as tf
from tensorflow import keras
from sklearn.metrics import mean_absolute_error, r2_score
import logging
tf.get_logger().setLevel('ERROR')
logging.getLogger('absl').setLevel(logging.ERROR)

def build_model(input_dim, layers=(64,32), act='relu', dropout=0.0, batchnorm=False, l2=0.0):
    reg = keras.regularizers.l2(l2) if l2 else None
    m = keras.Sequential([keras.layers.Input(shape=(input_dim,))])
    for u in layers:
        m.add(keras.layers.Dense(u, activation=act, kernel_regularizer=reg))
        if batchnorm: m.add(keras.layers.BatchNormalization())
        if dropout: m.add(keras.layers.Dropout(dropout))
    m.add(keras.layers.Dense(1))
    return m

def run_experiment(Xtr, ytr, Xval, yval, layers=(64,32), act='relu', dropout=0.0, batchnorm=False,
                    l2=0.0, optimizer='adam', lr=1e-3, batch_size=256, epochs=25, seed=42):
    tf.random.set_seed(seed)
    model = build_model(Xtr.shape[1], layers, act, dropout, batchnorm, l2)
    opt = {'adam': keras.optimizers.Adam, 'rmsprop': keras.optimizers.RMSprop,
           'sgd': lambda lr: keras.optimizers.SGD(lr, momentum=0.9)}[optimizer](lr)
    model.compile(optimizer=opt, loss='mse', metrics=['mae'])
    es = keras.callbacks.EarlyStopping(monitor='val_loss', patience=4, restore_best_weights=True)
    model.fit(Xtr, ytr, validation_data=(Xval, yval), epochs=epochs, batch_size=batch_size, callbacks=[es], verbose=0)
    pred = model.predict(Xval, verbose=0).flatten()
    return model, mean_absolute_error(yval*100, pred*100), r2_score(yval, pred)

baseline_model, baseline_mae, baseline_r2 = run_experiment(X_train_s, y_train, X_val_s, y_val)
print(f'Baseline MLP (64-32, Adam, batch 256) -> val MAE={baseline_mae:.2f}, val R2={baseline_r2:.3f}')

5. Experiments¶

Fourteen pipeline variants, each changing one design decision from the baseline — architecture depth/width, regularisation (dropout, batch-norm, L2), optimiser, learning rate, batch size, activation — plus two deliberate ablations: training on unscaled features, and training on audio features only (no genre). Those last two aren't hyperparameter tweaks, they're there to test whether two specific preprocessing/feature-engineering decisions actually matter.

The two ablations dwarf every hyperparameter tweak. Dropping the StandardScaler step doesn't just hurt — it breaks training outright (deeply negative R², MAE far above what guessing the mean would give), because unscaled loudness/tempo/duration values on wildly different numeric ranges destabilise gradient descent. Dropping genre and keeping only raw audio features costs roughly three-quarters of the R² the full feature set gets. By comparison, every architecture/regularisation/optimiser variant lands within a narrow band — meaningful, but nowhere near as decisive. That's the main methodological takeaway from this section: for this dataset, what features you feed the network and whether you scale them matter far more than which specific MLP configuration you pick.

7. Final Discussion¶

The tuned MLP explains roughly a third of the variance in popularity (test R² in the mid-0.3s), with a mean absolute error of around 11 popularity points on a 0–100 scale. That's a real improvement over just guessing the mean every time, but it's still far from a precise predictor. The permutation importance chart backs up what the ablation already showed: genre as a block is by far the most load-bearing feature, well ahead of any single audio attribute, with loudness and danceability coming in as the next most useful individual signals.

What I think this pipeline does well: the experiment table isolates why the model works, not just that it works. The scaling and genre ablations show exactly which design decisions are load-bearing versus cosmetic, which is more useful to a team picking up this pipeline than a single reported accuracy number would be. Train, validation and test stay strictly separate throughout, and the scaler is fit on the training set only, so the test score isn't inflated by leakage.

There are limitations worth being upfront about, though. Popularity is a moving target — Spotify's score reflects recent listening activity, not a track's lifetime ceiling, so a model trained on a snapshot will drift as tastes shift. Audio features alone also miss real drivers of popularity (artist fame, marketing spend, playlist placement itself), none of which are in this dataset at all, and that probably explains most of the unexplained variance rather than any real weakness in the network architecture. On top of that, the zero-inflated popularity floor noted in section 2 means the model is partly learning to predict a censored signal, not a clean underlying "quality" score.

At an average error of ~11 points, I wouldn't trust this model to replace human A&R judgement. But it's a reasonable triage signal: score newly ingested tracks automatically, and flag the ones predicted to land in the upper range for a human reviewer to prioritise, instead of reviewing the whole catalog in upload order. Given how clearly genre dominates, the most valuable low-effort improvement before doing anything else would be enriching the feature set with cheaper, currently-missing signals like playlist-add counts or artist follower counts, rather than continuing to tune the network architecture itself. On explainability, the permutation-importance view above gives a genuinely honest, model-agnostic read on what's driving predictions, even though the network itself isn't interpretable layer by layer. That's enough transparency to justify the triage use case, though I wouldn't deploy this for anything with real financial stakes without a richer feature set and some kind of periodic retraining to track drift.
